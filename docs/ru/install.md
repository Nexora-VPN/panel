# Установка Nexora

Nexora состоит из панели (плоскость управления) и произвольного числа узлов
(плоскость данных). Эта страница про установку панели. Узлы добавляются позже из
самой панели — для каждого она выдаёт команду в одну строку.

Установщик ничего не спрашивает. Единственное решение, которое он принимает за
вас, — база данных: это то единственное, что панель не может выбрать позже, ведь
без базы у неё вообще нет настроек. Всё остальное — главный администратор, порт,
секретные пути, HTTPS — выбирается в мастере настройки, который открывается при
первом заходе в панель.

## Требования

- 64-битный Linux-сервер с systemd (Debian 11+, Ubuntu 20.04+, RHEL 9+ или
  аналог). 32-битные ARM и x86 тоже поддерживаются.
- Доступ root.
- Открытый TCP-порт для панели (по умолчанию 2095). Панель слушает IPv6-wildcard,
  который обслуживает и IPv4, поэтому сервер только с v4, только с v6 или
  dual-stack работают одинаково и без настройки.

## Установка

С SQLite, которому не нужны другие сервисы:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/nexora-vpn/panel/main/install.sh)
```

С PostgreSQL, который установщик поставит и настроит сам:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/nexora-vpn/panel/main/install.sh) --postgres
```

Чтобы поставить конкретный релиз, добавьте `--version v1.2.3`.

Панель и нода выпускаются отдельно, поэтому и версии у них разные. Вместе с
панелью установщик готовит и бинарники ноды — именно их панель позже отдаёт
установщикам нод; `--node-version v1.2.3` фиксирует их версию. Без этого флага
берётся последний релиз ноды, что и нужно, если вы не воспроизводите конкретный
состав парка серверов.

SQLite — верный выбор по умолчанию: база панели Nexora невелика, а один файл
гораздо проще резервировать и переносить. PostgreSQL берите, если он у вас уже
есть или если панель обслуживает большую базу пользователей — и учтите, что это
единственное решение, которое панель не может пересмотреть сама, хотя перенести
данные потом можно резервной копией. [Выбор базы данных](database.md) — пороги,
то, что панель настраивает за вас на каждой из них, и порядок миграции.

## Завершение настройки

В конце установщик печатает ссылку вида:

```
http://203.0.113.10:2095/setup?t=9f3c1ad2…
```

Откройте её. Этот токен разрешает создать учётную запись главного администратора,
поэтому обращайтесь с ним как с паролем и не публикуйте нигде. Он перестаёт
работать, как только настройка завершена.

Пока настройка не закончена, панель не отвечает **больше ни на что**: любой другой
путь — страница входа, API, ссылки подписок — возвращает 404, и сама страница
настройки без токена тоже. Ненастроенная панель на публичном IP не даёт сканеру
ничего.

Установщик печатает по ссылке на каждый найденный адрес плюс одну на тот адрес,
которым этот хост виден из интернета. Используйте ту, что действительно доходит
до сервера: на VPS это обычно публичный адрес, а на хосте с контейнерами
большинство остальных — виртуальная адресация моста, которая никуда не ведёт.

Адрес IPv6 попадает в эти ссылки в квадратных скобках — так требует URL:
`http://[2001:db8::10]:2095/setup?t=…`. Вставляйте ссылку целиком; без скобок
браузер её не примет.

Если ссылки потеряны, напечатайте токен на сервере и соберите URL вокруг него:

```bash
nexora-panel setup-token
# → 9f3c1ad2…   затем откройте http://YOUR-SERVER:2095/setup?t=9f3c1ad2…
```

Мастер собирает всё в одной форме и сохраняет за один шаг:

- **Главный администратор** — учётная запись, которая настраивает панель и видит
  все подписки. Не менее 12 символов, минимум три из: строчные, прописные,
  цифры, символы.
- **Адрес панели** — IP и порт для прослушивания и секретный путь, по которому
  панель отвечает. Предлагается случайный путь: сохранив его, вы добиваетесь
  того, что нашедшие ваш порт сканеры всё равно не найдут страницу входа.
- **Путь подписок** — на нём строятся ссылки подписок. Должен отличаться от пути
  панели.
- **HTTPS** — включён по умолчанию. Панель выпускает собственный сертификат и
  продлевает его до истечения срока.
  - **Адреса сертификата** заполнены адресом, по которому вы открыли мастер, и
    всеми публично маршрутизируемыми адресами машины. Отредактируйте их: панель
    не может знать, каким адресом воспользуются ваши клиенты. Внутри контейнера
    она видит только адресацию моста, а за NAT публичного адреса нет ни на одном
    интерфейсе — если адрес, который вы набираете в браузере, не в списке,
    добавьте его. Адреса IPv6 пишутся как есть (`2001:db8::10`); скобки
    принимаются и отбрасываются.
  - Добавьте домен — и сертификат будет перевыпущен под него; домен подписок
    помещается в тот же сертификат.
  - HTTPS можно отключить, но тогда пароли и ссылки подписок передаются открытым
    текстом.
- **Часовой пояс** — в нём отображается каждая дата в панели.

Сохранение перезапускает панель на только что описанный адрес, и браузер
переходит туда. С самоподписанным сертификатом браузер предупредит один раз —
примите его и продолжайте.

## Как перемещаться по панели

Две вещи, которые стоит знать в первый же день, потому что ни одна из них не
лежит там, где её стали бы искать.

**Нажмите Ctrl-K** (на Mac — Cmd-K) в любом месте панели или щёлкните лупу в
шапке. Одно поле ищет по всем страницам, по всем формам «создать…» и по вашим
пользователям — по имени, по группе и **по идентификатору подписки**, что
превращает «клиент прислал только эту ссылку» в одну вставку. Стрелки
перемещают, Enter открывает, Escape возвращает ровно туда, где вы были. Простой
`/` тоже открывает его — когда вы не печатаете в поле.

**Установите панель как приложение.** В Chrome, Edge или браузере Android
адресная строка предложит установку; на iPhone — Поделиться → На экран
«Домой». Дальше она открывается в собственном окне без адресной строки и на
базовом пути вроде `/panel` работает точно так же, как в корне. Это та же
панель в другой рамке: офлайн-режима нет, потому что каждая страница панели
управления — это живое чтение флота, который меняется, пока вы на него
смотрите. Для установки нужен HTTPS — панель по обычному `http://` такого
предложения просто не сделает.

Цвет и плотность — в меню темы рядом с переключателем языка: пять палитр и
компактный режим, который заметно увеличивает число строк на экране ноутбука.
И то и другое — свойство браузера, а не учётной записи.

## Маскировка панели

Секретный базовый путь уже не даёт сканеру, нашедшему ваш порт, найти и страницу
входа. Чего он не исправляет — это сам порт: любой другой адрес отвечает 404, а
хост, который завершает TLS-рукопожатие и затем на всё отвечает 404, — не
обычный сервер. Сигнал небольшой, но именно он остаётся, когда никакой страницы
входа найти уже нельзя.

**Настройки → панель → каталог маскировки** принимает абсолютный путь, и любой
адрес на этом порту, который не является панелью, подпиской или зеркалом наборов
правил, отдаётся из него как обычный сайт. `https://panel.example.com/`
становится тем, что вы положили в этот каталог; панель остаётся на своём базовом
пути. Применяется после перезапуска панели.

Своей страницы панель намеренно не поставляет. Заглушка, поставляемая вместе с
панелью, была бы на всех установках побайтово одинаковой, и сканер начал бы
опознавать её вместо тишины — примета лучше той, которую она заменила. Положите
туда что-то, подходящее этому адресу: лендинг, сайт компании, копию того, что вы
и так хостите.

**Положите туда и `404.html`.** Любой путь в этом каталоге, за которым нет
файла, отвечает 404, и без `404.html` отвечает он собственным
`404 page not found` веб-сервера Go, простым текстом — то есть выдаёт
программу на первом же запросе сканера, а это ровно та примета, ради которой
маскировка и существует. Если `404.html` в каталоге есть, отдаётся он, с тем же
статусом 404. Каталог без него ведёт себя ровно так же, как раньше.

Три вещи, которых она не делает, и каждая намеренно:

- **Она не трогает API.** Запрос, который приняла панель, принадлежит панели,
  поэтому `GET /panel/api/users` без учётных данных по-прежнему отвечает 401 в
  JSON. Превращение отказов аутентификации в веб-страницы сломало бы все
  интеграции и сам интерфейс панели.
- **Она не показывает список каталога и не отдаёт dot-файлы.** Список — это
  способ прочитать весь каталог разом, а каталог, скопированный с хоста, чаще
  всего приезжает с `.git` или `.env` внутри. Симлинк, ведущий наружу, не
  разыменовывается.
- **Без базового пути она ничего не делает.** Когда панель в корне, прикрывать
  на этом адресе нечего. Сначала задайте базовый путь.

Относительный путь отклоняется при сохранении, и `/` тоже. Относительный
разрешался бы от рабочего каталога самой панели — того, где лежит её база
данных.

## Docker

Два стека, по одному на базу данных. Выберите каталог и запустите:

```bash
git clone https://github.com/nexora-vpn/panel
cd panel/docker/sqlite      # или: cd panel/docker/postgres
docker compose up -d
docker compose logs panel | grep setup
```

Для стека с PostgreSQL перед первым запуском скопируйте `.env.example` в `.env`
и задайте пароль.

Каждый стек держит рядом со своим compose-файлом то, что должно пережить
контейнер: базу SQLite в `./data` (стек с PostgreSQL вместо этого использует
именованный том), бинарники узлов в `./bin`, архивы резервных копий в
`./backups` — см. раздел «Резервные копии» — и зеркальные файлы наборов правил,
которые панель отдаёт своим узлам, в `./rulesets`. Последнее — кэш: очистить его
безопасно, при следующем запуске панель скачает недостающее заново.

В Docker порт панели закреплён переменной `NEXORA_WEB_LISTEN` в compose-файле,
потому что там же находится и публикация порта. Смена порта в интерфейсе панели
лишь сделает контейнер недоступным — меняйте оба вместе.

`NEXORA_WEB_LISTEN` привязывает адрес *внутри* контейнера; до хоста доходит
публикация `ports:`, а Docker без явного указания публикует только на IPv4. На
хосте только с IPv6 включите IPv6 в демоне (`"ipv6": true` и `"ip6tables": true`
в `/etc/docker/daemon.json`) и публикуйте на обоих:

```yaml
    ports:
      - "0.0.0.0:2095:2095"
      - "[::]:2095:2095"
```

### Панель и нода на одном сервере

`docker/panel-and-node` — это стек с SQLite, рядом с которым стоит нода. Так
делать **не рекомендуется**: адрес ноды попадает в каждую выданную подписочную
ссылку, поэтому нода здесь раскрывает адрес панели всем пользователям; а
клиентский трафик ничем не ограничен, поэтому нода под нагрузкой утянет за собой
и панель, и подписки пользователей всех остальных нод. Для лаборатории, демо или
небольшой односерверной установки это разумный размен. Полный список оговорок —
в [руководстве по установке ноды](https://github.com/nexora-vpn/node/blob/main/docs/ru/install.md#панель-и-нода-на-одном-сервере).

Ноде нужен клиентский сертификат панели, а панель отдаёт его только после того,
как нода в ней добавлена, — поэтому стек запускается в два шага:

```bash
cd panel/docker/panel-and-node
docker compose up -d panel
docker compose logs panel | grep setup      # откройте ссылку, пройдите мастер

# затем в панели: добавьте ноду с адресом 127.0.0.1 и портом 62050 и сохраните
# клиентский сертификат с её страницы установки как ./certs/panel_ca.pem
docker compose up -d node
```

Оба сервиса работают в сети хоста: нода — потому что порты её inbound'ов
выбираются в панели уже потом, панель — чтобы дотянуться до ноды на 127.0.0.1.
Публикации портов при этом нет, и синхронизировать нечего, так что это
единственный стек, который *не* закрепляет `NEXORA_WEB_LISTEN`: выбранный в
мастере порт слушается прямо на хосте, как при обычной установке. Управляющий
порт ноды не выходит за пределы машины и не требует правил файрвола.

## Обновление

Панель раз в сутки проверяет, вышел ли новый выпуск, и показывает баннер, если
вышел. **Настройки → Обновление панели** содержит всё: установленную версию
против последнего выпуска, способ установки и — на systemd-установке — кнопку,
которая делает всё сама:

1. снимает резервную копию базы в ваш каталог резервных копий,
2. скачивает выпуск и сверяет его с контрольной суммой, опубликованной рядом,
3. один раз запускает скачанный бинарник, чтобы убедиться, что это панель,
   которая стартует на этой машине,
4. подменяет его, оставляя прежний в
   `/opt/nexora-panel/nexora-panel.previous`,
5. перезапускается. Сессия сохраняется; панель недоступна несколько секунд, и
   страница сообщит, когда та вернётся.

Если новая сборка не поднимется, прежний бинарник возвращается **автоматически**
— примерно за десять секунд, а не за минуты. Но **база не откатывается**:
миграции идут только вперёд. Поэтому если после обновления что-то не так, путь
назад — та самая копия из первого шага, в разделе **Настройки → Резервные
копии**.

Установка в Docker не может заменить собственный образ, и страница прямо об
этом говорит, вместо того чтобы пытаться наполовину. Обновляйте её обычным
способом:

```bash
docker compose pull && docker compose up -d
```

Ежедневная проверка — это один запрос к списку выпусков этого репозитория,
который сообщает GitHub адрес вашего сервера. Выключите её переключателем на
той же странице или из командной строки:

```bash
nexora-panel config set update_check false
```

Кнопка на странице работает и с выключенной проверкой — эта настройка о том,
что панель делает сама, а не о том, что вы можете у неё попросить.

### Из командной строки

Запустите установщик ещё раз. Он обнаружит существующую установку и обновит её
на месте:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/nexora-vpn/panel/main/install.sh)
```

Он остановит службу, сохранит копию базы SQLite в `nexora.db.bak`, оставит
прежний бинарник в `/opt/nexora-panel/nexora-panel.previous`, выполнит миграции и
запустит службу снова. `config.json`, настройки и учётные записи не затрагиваются.
Для PostgreSQL сделайте дамп самостоятельно.

## Потеряли доступ?

Любая настройка, способная сделать панель недоступной, записывается из командной
строки, без запущенной панели:

```bash
nexora-panel config list                       # что задано
nexora-panel config set web_listen_port 2095   # порт, до которого вы дотянетесь
nexora-panel config set web_listen_ip ""       # снова слушать везде (v4 и v6)
nexora-panel config set web_domain ""          # снять ограничение по имени хоста
nexora-panel config set web_basepath ""        # снова отдавать в корне
nexora-panel config set sub_domain ""          # перестать резервировать хосты под подписки
systemctl restart nexora-panel
```

Последняя строка — наименее очевидный способ потерять панель, и срабатывает он
только если **базового пути нет**. Домен, перечисленный в `sub_domain`, отдаёт
подписки и больше ничего, чтобы ссылка конечного пользователя не выдавала, где
администрируется панель, — а когда панель находится в корне каждого хоста, на
этих именах до неё просто негде добраться. Перечислите там единственные адреса,
которыми вы реально пользуетесь (`localhost`, IP вашего сервера), и панель
станет недоступна сразу отовсюду.

Задайте базовый путь — и ловушки нет: панель остаётся доступной по этому
префиксу на любом хосте, включая домены подписок. Клиенту со ссылкой пришлось бы
угадать префикс, а он и так единственное, что защищает панель на IP вашего
сервера.

Установщик кладёт `nexora-panel` в PATH, а бинарник сам находит свой файл
конфигурации, так что команды работают из любого каталога. В Docker используйте
префикс `docker compose exec panel /app/`.

**Забыли пароль.** Тот же офлайновый путь, только для учётной записи, а не для
адреса:

```bash
nexora-panel admin list                        # какие учётные записи есть и кто владеет панелью
nexora-panel admin reset-password              # владелец панели; пароль вводится и не отображается
nexora-panel admin reset-password -user alice  # любая другая запись
```

Без `-user` берётся **владелец** панели — единственная запись, которую нельзя
удалить или понизить и которую отмечает `nexora-panel admin list`, — так что у
«главного администратора» есть однозначный ответ даже когда их несколько. На
установке старше владельца команда возвращается к единственному главному админу,
а если их несколько — отказывается и называет их. Новый пароль спрашивается дважды и никогда не
печатается; `-pass` задаёт его сразу — для установки без участия человека, ценой
того, что пароль останется в истории оболочки. Сброс делает три вещи, потому что потерянный пароль и потерянный телефон — это
одна и та же авария: задаёт пароль, **выключает двухфакторную аутентификацию**
для этой учётной записи (секрет и коды восстановления стираются, оператор
регистрирует их заново из панели) и **закрывает все её открытые сессии**.
Работающая панель держит сессию в кэше до минуты активности — команда об этом
говорит; если эта минута важна, перезапустите её.

**Блокировка баном.** Пять неудачных входов с одного адреса блокируют его, и
поскольку бан хранится в базе, перезапуск его не снимает. Кто этот адрес и кого
нельзя заблокировать, решают две настройки:

```bash
nexora-panel config set trusted_proxies "10.0.0.0/8"   # ваш nginx / CDN, или пусто
nexora-panel config set login_allowlist "203.0.113.7"  # адреса, которые не банятся
```

**Панель за обратным прокси или CDN без `trusted_proxies` видит всех
посетителей как один адрес** — и первая же блокировка закроет вход всем.
Укажите там адрес прокси, а свою сеть держите в `login_allowlist` как путь
назад. Главный админ также может снять бан в **Настройки → Безопасность**.

## IPv6

Настраивать здесь нечего. По умолчанию панель слушает `[::]:2095`, что на
dual-stack хосте отвечает и по IPv4; хост с выключенным IPv6 такой адрес привязать
не может, и панель сама откатывается на `0.0.0.0:2095`. Чтобы слушать только одно
семейство, задайте в `web_listen_ip` конкретный адрес (`::` или `0.0.0.0`, либо
один определённый) — в мастере или из командной строки.

С нодами та же история с другой стороны: нода только с адресом IPv6 добавляется с
адресом, записанным как есть (`2001:db8::1`, скобки необязательны), а панель
ставит скобки там, где этого требует синтаксис: ссылки получаются как
`vless://…@[2001:db8::1]:443?…`, профиль wireguard — как
`Endpoint = [2001:db8::1]:51820`, тогда как профиль clash, sing-box или OpenVPN
несёт голый адрес. Подписочные URL, построенные на адресе IPv6 панели, берутся в
скобки по той же причине.

## Ваш первый входящий

**Входящие → Из пресета.** Пресет — это протокол с уже выбранным транспортом и
решением по TLS: VLESS + REALITY, VLESS или Trojan поверх WebSocket за CDN,
gRPC, Hysteria2. Первый входящий превращается в выбор и сохранение вместо
четырёх вкладок с решениями.

Выбор пресета **ничего не создаёт**. Он заполняет обычную форму входящего, вы её
подтверждаете, и в базе оказывается обычная запись: ничто потом не помнит, из
какого пресета она пришла, и все поля остаются редактируемыми. Порт, тег и путь
транспорта генерируются для каждой установки, а для REALITY панель создаёт пару
ключей и short ID при сохранении — искать и вставлять ключ не нужно.

Сама полка — это файл, который отдаёт панель, так что её можно дополнять.
Положите `.json` в `/var/opt/nexora/presets/` (или туда, куда указывает
**Настройки → Каталог пресетов**), и он наложится на встроенный список по ключу:
новый ключ добавляется, существующий заменяется. Так же переводят запись набора
правил на зеркало там, где upstream заблокирован. Файл, который не разбирается,
пропускается со строкой в журнале панели, а не уносит каталог с собой; страница
настроек называет файлы, которые действительно применены.

### XHTTP: расширенные поля

**Расширенные** поля входящего XHTTP — это ручки транспорта Xray-core в
написании sing-box. Каждое из них узел применяет *и* сообщает клиенту в ссылке,
чтобы обе стороны сходились, — и у этого есть одно следствие, которое стоит
прочитать дважды: **измените любое из них, и каждую ссылку этого входящего
придётся выпустить заново.** Клиенту со старой ссылкой узел отказывает, причём
XHTTP отказывает не чистой ошибкой, а случайными 4xx, так что в поддержку
приходит «иногда работает». Определитесь с ними до того, как клиенты
импортируют входящий, или планируйте повторный импорт.

Что они делают:

- **X-Padding bytes** — диапазон размера набивки, которую обе стороны добавляют
  к каждому запросу, по умолчанию `100-1000`. Шире — больше байтов на запрос и
  менее регулярные размеры. На набивку вне своего диапазона узел отвечает 400,
  поэтому значение и должно ехать в ссылке.
- **X-Padding obfuscation** с его **key, header, placement и method** —
  выключено: набивка — фиксированная пара `Referer`/`x_padding`, четыре поля
  игнорируются. Включено: она переезжает в заголовок, параметр запроса, cookie
  или путь (placement) под выбранным вами именем (key/header) и генерируется
  одним из двух методов (`repeat-x`, `tokenish`).
- **Session placement/key** и **Sequence placement/key** — где едут
  идентификатор сессии и номер пакета: сегмент пути (по умолчанию), параметр
  запроса, заголовок или cookie, под названным вами ключом.
- **Uplink HTTP method**, **data placement** и **data key** — как клиент
  отправляет свою половину загрузки: телами `POST` (по умолчанию) или `GET` с
  данными в заголовке или cookie.
- **Max bytes per post** — самый большой кусок загрузки, по умолчанию
  `1000000`.

В ссылку попадают только изменённые вами значения; значение по умолчанию —
никогда. Так более поздняя смена умолчания, наша или Xray, применяется к старым
и новым ссылкам одинаково, вместо того чтобы вбить сегодняшнее число в каждую
когда-либо выпущенную ссылку.

**За CDN** набивка, идентификатор сессии и номер пакета проходят в любом
размещении: это короткие значения в пути, запросе, заголовке или cookie, а их
пересылает любой CDN, который вообще пересылает HTTP. Две формы, которые CDN
нести не может, — *полезная нагрузка* загрузки в **заголовке** или в
**cookie**, и панель отказывает в них при сохранении фронта — см. раздел «Что
нельзя фронтить» в [ссылках и подписках](subscriptions.md).

**Кто их читает.** Клиенты на Xray — v2rayNG, v2rayN, Streisand, Happ — знают
XHTTP и получают каждое поле. У приложений sing-box и Clash XHTTP нет, поэтому их
файлы подписки пропускают входящий, а не несут его половину.

**Одно поле, которого форма не предлагает** — `trusted_x_forwarded_for`, в JSON
входящего под `transport` — становится важным в тот момент, когда входящий XHTTP
оказывается за CDN или reverse proxy. Это список имён заголовков, которые фронт
ставит на каждый запрос (`CF-Connecting-IP` у Cloudflare); когда один из них
присутствует, узел читает адрес клиента из `X-Forwarded-For`, а с ним — лимит
адресов и логи. **Пустое значит доверять любому** `X-Forwarded-For`, от кого
угодно: клиент на напрямую доступном входящем может назвать свой адрес источника
сам. Xray-core в 26.6.22 сменил своё умолчание на *не доверять никому*; этот
узел оставил старое правило. **Панель заполняет поле за вас, когда фронт
говорит, каким заголовком его CDN помечает запросы** (поле фронта *заголовок
адреса клиента*, `CF-Connecting-IP` у Cloudflare): его получает каждый входящий
XHTTP, на котором включён этот фронт, если входящий не задал своё. Так что
назовите заголовок на фронте, а входящий без фронта не ставьте ни за что другое.

### VLESS Encryption

Inbound VLESS может шифровать сам поток VLESS — **VLESS Encryption**, на
вкладке **Protocol** inbound — поверх TLS или без него. Две вещи, которых
больше ничто в панели не даёт: там, где CDN завершает TLS (фронты на странице
Fronts), CDN видит шифртекст вместо вашего трафика VLESS; и каждое соединение
проходит постквантовый обмен ключами (ML-KEM-768 с X25519), с TLS или без.

Включается выбором **аутентификации** — какой ключ удостоверяет сервер:
**X25519** (не постквантовый) или **ML-KEM-768** (постквантовый). Выберите
один; обмен внутри каждого соединения постквантовый в любом случае. Панель
создаёт ключ, хранит строку сервера как `decryption` inbound, отправляет её
на узел и выводит строку клиента, которую несёт каждая ссылка и outbound.
Строка сервера в ссылке не появляется никогда. **Режим** (`native`, `xorpub`,
`random`) определяет, какая часть рукопожатия скрыта за XOR-потоками;
**срок билета** — сколько клиент может переподключаться без полного
рукопожатия.

С ним идут два правила. **Оно перевыпускает все ссылки**: клиент со ссылкой,
полученной до изменения, отвергается на рукопожатии, так что настройте это до
того, как клиенты импортируют inbound, или запланируйте повторный импорт — то
же правило, что у расширенных полей XHTTP. И **приложения на sing-box его не
используют** (Karing, NekoBox, SFA — sing-box закрыл запрос), поэтому их
подписки пропускают inbound, а не несут то, что не соединится; приложения на
Xray-core (v2rayNG, v2rayN, Streisand, Happ) и mihomo 1.19.14+ получают его
целиком. И ещё: `xtls-rprx-vision` на зашифрованном inbound отбрасывается, и
на узле, и в ссылках — сервис VLESS узла запускает vision только прямо на
TLS-соединении.

### Смена портов

Входящий Hysteria или Hysteria2 может слушать набор портов помимо своего —
**Listen ports**, в написании sing-box `start:end`, например `20000:20999`, — и
клиент, знающий набор, переходит между ними, так что заблокированный порт стоит
одного порта. Узел отвечает на всех без перенаправления iptables, а ссылка несёт
набор (`mport=` в ссылке, `server_ports` в файле sing-box, `ports` в файле
Clash).

Как часто клиент переходит — решение клиента, а не узла, поэтому оно живёт на
вкладке **Client** входящего: **Hop interval** (`30s` у любого клиента, которому
ничего не сказали) и, только для Hysteria2, **максимум** — с обоими значениями
клиент выбирает каждый переход случайно между ними, и переходы перестают быть
периодическими. Оба попадают в файл sing-box (`hop_interval`,
`hop_interval_max`) и в файл Clash (`hop-interval` — число, или `30-60`, когда
задан максимум; mihomo читает диапазон с 1.19.24). В ссылке места нет ни для
одного, поэтому клиент, импортирующий ссылку, остаётся при своём умолчании.
Панель отказывает при сохранении в том, в чём клиент sing-box отказал бы при
запуске, на устройстве клиента: максимум без интервала, максимум ниже него или
что-либо меньше пяти секунд.

## Пресеты маршрутизации и DNS

**Шаблоны → шаблон → Маршрутизация (или DNS) → Из пресета.** Та же идея полки,
что и у входящих: блок маршрутизации из списков, которые панель уже зеркалирует —
блокировать рекламу и выпускать иранские (китайские, российские) домены и адреса
прямо на узле, а не дальше, — плюс набор шифрованных резолверов для DNS.

Применение пресета маршрутизации **заменяет** правила шаблона. Это намеренно:
порядок правил *и есть* маршрутизация, поэтому смешивание ваших правил с
правилами пресета дало бы порядок, который не выбирал никто. Нужные наборы правил
добавляются к выбору, а не заменяют его.

Знать стоит вот что: что происходит, когда пресету нужен список, которого у вас
нет. Панель исключает набор правил, копии которого у неё нет, **и каждое правило,
ссылающееся на него** — иначе нельзя, потому что узел отвергает всю свою
конфигурацию, если правило называет неопределённый набор. Значит, пресет,
применённый без своих списков, — это шаблон, который ничего не блокирует и нигде
не объясняет почему. Диалог проверяет заранее: называет недостающие списки и
предлагает скачать их перед применением, а если списка нет и в каталоге —
отказывает.

DNS-пресеты — это Cloudflare, Google, Quad9 и AdGuard поверх DNS-over-TLS плюс
системный резолвер самого узла. AdGuard режет рекламу на резолвере, что является
альтернативой пресету маршрутизации против рекламы, а не дополнением к нему.

**Блокировать торренты** работает по мере возможного, и его диалог так и
говорит. Он сниффит каждое соединение и отправляет то, что похоже на BitTorrent,
в блокирующий outbound, который узел считает: цифра — в строке узла, в
`/metrics` и, выше заданной вами частоты, в событии `node.rejections_high`.
Сниффинг — это распознавание протокола, а не гарантия: клиент, шифрующий
рукопожатие (MSE/PE, включено по умолчанию в большинстве сегодняшних клиентов),
или клиент, которого сниффер не видел, проходит. Панели, обещающие больше,
крутят рядом с ядром движок deep packet inspection; эта — нет. Читайте счётчик
как «что поймано», а не «что было».

**Иран + блокировать рекламу** хорош настолько, насколько хорош список, а список
неполон. Он выпускает `geoip-ir` и `geosite-category-ir` прямо на узле, чтобы
внутренний трафик оставался внутри, — для префиксов, которые знает набор
SagerNet. По замеру 2026-09-22 более полный набор сообщества,
[Chocolate4U/Iran-sing-box-rules](https://github.com/Chocolate4U/Iran-sing-box-rules),
несёт примерно на 12% больше иранских префиксов (343), хуже всего покрыты
хостеры вроде ParsPack. Ничего не сломано, пресет делает то, что говорит. Но
если вы применяете его ради того, чтобы ни одно внутреннее назначение никогда
не уходило через узел, добавьте полный список сами: файл каталога в каталоге
пресетов (выше), который перенаправляет `geoip-ir` на
`https://raw.githubusercontent.com/Chocolate4U/Iran-sing-box-rules/rule-set/geoip-ir.srs`,
и панель зеркалирует его как любой другой.

## Когда отключён весь интернет

В день, когда международный канал отключён, а не отфильтрован, ничто в этой
панели не поможет: каждому входящему нужен путь наружу, а его нет. Что
продолжало работать в такие дни — DNS: резолверы внутри страны всё ещё,
медленно, пересылают запросы наружу, — и инструмент для этого — **DNS-туннель
рядом с узлом**, а не внутри него. У панели намеренно нет для него страницы:
функция ради дня, который случается раз в год, остальной год — груз для
поддержки, а существующие инструменты — на расстоянии одного shell-скрипта.

Форма такая: на сервере узла
[dnstt-deploy](https://github.com/bugfloyd/dnstt-deploy) (dnstt — медленный,
надёжный, UDP/53) или [slipgate](https://github.com/anonvector/slipgate) (dnstt и
Slipstream, более быстрый QUIC-over-DNS, под одним менеджером) ставит сервер
туннеля как unit systemd. Его целью укажите входящий, слушающий loopback, —
входящий SOCKS или Shadowsocks с `listen`, равным `127.0.0.1`, на том же узле,
выданный тем же пользователям, — чтобы туннель передавал соединения узлу и
каждый байт по-прежнему считался на пользователя. (Каждое соединение тогда
приходит с `127.0.0.1`, так что лимит адресов видит один адрес на всех за
туннелем.) Со стороны DNS нужна NS-запись, делегирующая поддомен,
`t.example.com`, серверу, и свободный на нём порт 53 — узел там ничего не
занимает; пресеты DNS называют удалённые резолверы.

Клиентские приложения — NetMod, HTTP Injector, SlipNet, приложение dnstt —
спрашивают три значения, и все три принадлежат туннелю, а не панели: домен
туннеля, публичный ключ сервера, который печатает установщик, и резолвер, куда
слать запросы (в обычный день — URL DoH или DoT; в день отключения — адрес
простого внутреннего резолвера). Через туннель приложение говорит с вашим
loopback-входящим ровно так же, как с публичным, поэтому от вас ему нужна ссылка
этого входящего, где адрес заменён на локальную точку, которую открывает
приложение.

## Ссылки и подписки

Когда парк поднят, то, что получают ваши клиенты, — отдельная тема:
**[ссылки и подписки](subscriptions.md)**. Там про объявление нескольких адресов
на узел, про CDN перед входящим (включая wildcard-запись DNS, которая нужна для
отдельного имени хоста каждому клиенту, и почему панель отказывается фронтить
входящий на REALITY или Hysteria), про названия записей по шаблону и про
единственную клиентскую настройку — **Mux** в приложениях на Xray, — которая
молча ломает эти конфигурации.

## Операторы и роли

**Настройки → Администраторы** создаёт учётные записи операторов, а **Роли**
решают, что каждая из них может делать. С панелью поставляются три роли, и для
большинства установок их достаточно:

| Роль | Для чего |
| --- | --- |
| Главный администратор | Управляет всем, включая администрирование самой панели: операторами, ролями, токенами API, лицензией, резервными копиями и настройками безопасности. |
| Оператор | Управляет сервисом: пользователями, узлами, шаблонами, пулом, сертификатами и настройками — но не администрированием панели. |
| Реселлер | Владеет только своей книгой пользователей. Лимит трафика, срок действия и лимит пользователей задаются на самой учётной записи. |

**Своя роль** начинается с одной из этих трёх и отбирает права. Добавить права
она не может: панель откажется сохранить роль, выдающую право, которого нет у
вас самих, и откажется назначить такую роль аккаунту. Поэтому «оператор, который
не трогает узлы» — это роль, а «оператор, который ещё и управляет лицензией» —
нет.

Что доступно учётной записи, решают две разные вещи:

- **Права решают, какие страницы.** Роль без «Настраивать узлы», но с «Видеть
  узлы», откроет список узлов, и каждая кнопка на нём ответит «вашей роли не
  хватает права nodes:write».
- **Владение решает, какие пользователи.** Реселлер видит только свои учётные
  записи — это свойство того, что он реселлер, а не право. Выдача роли реселлера
  права «Видеть пользователей» не покажет ему чужих клиентов.

Роль может нести и **ограничения**, которые правами не являются: сколько
пользователей может иметь аккаунт с этой ролью, какой максимальный лимит
устройств он может назначить пользователю и какой самый длинный тариф может
продать. 0 — без ограничения. Ограничение роли — это потолок над собственной
квотой аккаунта, оно её никогда не повышает, а пользователь вообще *без* лимита
устройств будет отклонён, а не тихо ограничен: «без лимита» здесь — настоящий
выбор, и делать его за вас не следует.

Изменение роли завершает сеансы всех, кто её носит; новые права они получат при
следующем входе. Роль, назначенную хоть одному аккаунту, удалить нельзя, и отказ
называет эти аккаунты, чтобы было понятно, куда смотреть. Три встроенные роли
есть всегда, их нельзя изменить или удалить — задать можно только их
ограничения.

**Владелец.** Панелью владеет одна учётная запись. Её нельзя удалить или
понизить, и только она может передать панель другому главному администратору
(значок короны в списке администраторов). Передача — это именно *передача*: вы
остаётесь главным администратором, но передавать дальше сможет только новый
владелец. На существующей установке владельцем становится самый старый главный
администратор, выбранный автоматически — настраивать нечего.

К владельцу же обращается `nexora-panel admin reset-password`, когда имя учётной
записи не указано, — поэтому `nexora-panel admin list` его отмечает.

## Мониторинг

Панель публикует свои показатели — какие узлы на связи, диск и память по каждому,
трафик, аккаунты по статусу, запас по лицензии, шину событий — на `/metrics` в
формате Prometheus. В **[мониторинге](monitoring.md)** есть compose-оверлей,
который поднимает Prometheus и Grafana рядом с вашей панелью с уже готовым
дашбордом, и четыре полезных алерта. Два момента заранее: эндпоинт требует
API-токен (он называет каждый ваш узел), а показателя, который узел не сообщил,
не будет вовсе — это не ноль.

## Резервные копии

Панель делает резервные копии собственной базы — **Настройки → Резервная копия** в
боковом меню (только главный администратор: архив содержит все учётные данные,
какие у панели есть).

Архив — это логический дамп всех таблиц внутри gzip-tar, а не копия файла базы.
Поэтому копия, снятая на SQLite, восстанавливается на PostgreSQL и обратно — и
поэтому же это и есть способ перенести панель на другой сервер.

```
Настройки → Резервная копия
├─ Скачать              прямо в браузер; на сервере ничего не остаётся
├─ Снять на сервере     пишется в каталог резервных копий
├─ Расписание           по умолчанию выключено: интервал в часах и сколько хранить
└─ Проверка / восстановление   сначала осмотреть архив, потом заменить им базу
```

**Где они лежат.** В обычной установке — `/var/opt/nexora/backups`. В Docker стеки
монтируют `./backups` рядом с тем `docker-compose.yml`, который вы запустили, так
что архивы остаются на хосте и переживают контейнер. В обоих случаях копируйте
этот каталог куда-нибудь ещё: резервная копия, существующая только на защищаемой
ею машине, — не резервная копия.

**Шифрование.** Пароль необязателен и действует на скачивание, на копии, снятые
на сервере, и на копии по расписанию (scrypt + AES-GCM). Панель хранит его только
чтобы шифровать; восстановить утраченный пароль она не может, а архив, который не
расшифровывается, не восстанавливается — держите пароль там же, куда увозите
архивы, а не на самой панели.

**Проверка перед восстановлением.** *Проверка* читает архив, ничего не трогая:
что в нём, когда и какой версией панели он снят, и какие есть предупреждения —
архив с другого хоста (его лицензия здесь не пройдёт), архив без главного
администратора, архив, снятый без истории трафика или без журнала действий.

**Восстановление** заменяет каждую строку в базе и перезапускает панель. Перед
этим оно пишет **снимок до восстановления** текущей базы в тот же каталог;
ротация такие снимки не удаляет никогда, так что неудачное восстановление
отменяется восстановлением снимка. По умолчанию сохраняются собственные адресные
настройки *этой* установки (порт, домен, путь, TLS) и её лицензия — чтобы архив с
другой машины не увёл панель на адрес, которого у этого сервера нет.

**Переезд на другой сервер.** Установите панель на новом сервере, откройте ссылку
первичной настройки и на первом экране мастера вместо заполнения формы выберите
*Переезжаете с другого сервера? Восстановите из копии*. Это единственное место,
где восстановление работает до появления учётной записи, — а именно в таком
состоянии и находится свежая установка; здесь берутся настройки самого архива,
потому что у пустой установки сохранять нечего. Лицензия не переезжает: она
привязана к отпечатку железа хоста, поэтому установите свой ключ на новом сервере
(`nexora-panel hwid` печатает нужный отпечаток).

**Из командной строки** — для установки без графики или скриптовой:

```bash
nexora-panel config set backup_enabled true
nexora-panel config set backup_interval_hours 24    # ежедневно
nexora-panel config set backup_keep 14              # 0 — хранить всё
nexora-panel config set backup_dir /var/opt/nexora/backups   # только абсолютный путь
nexora-panel config set backup_passphrase "длинный пароль"
```

Расписание перечитывается на ближайшем часовом тике панели, так что перезапуск не
нужен ни для одной из этих команд. `backup_passphrase` никогда не печатается ни в
`config list`, ни в `config get`. В Docker добавляйте перед ними
`docker compose exec panel /app/`.

**Восстановление из командной строки** — для случая, когда панель не работает
вовсе: база потеряна или панель падает при запуске.

```bash
systemctl stop nexora-panel
nexora-panel restore /var/opt/nexora/backups/nexora-backup-20260914-030000.tar.gz
systemctl start nexora-panel
```

Сначала архив читается целиком: команда печатает, что в нём, и все
предупреждения, а затем просит набрать `replace-database`. Запуск без терминала —
скрипт, конвейер — вместо вопроса требует `-yes`. Зашифрованный архив принимает
`-passphrase` или спрашивает его. Как и в панели, собственные настройки адреса и
лицензия этой установки сохраняются (`-keep-web-settings=false` и
`-keep-license=false` берут архивные), а перед любыми изменениями пишется
снимок предыдущей базы.

Сначала остановите панель. На SQLite подмена происходит при следующем запуске
панели, поэтому всё, что работающая панель успеет записать, остаётся в заменённой
базе; на PostgreSQL строки заменяются сразу, прямо под ней.

## Удаление

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/nexora-vpn/panel/main/install.sh) --uninstall
```

Служба и `/opt/nexora-panel` удаляются. База данных *и резервные копии* в
`/var/opt/nexora` намеренно остаются — удалите их сами, когда убедитесь, что они
больше не нужны, а если уходит и сам сервер, сначала увезите с него
`/var/opt/nexora/backups`.

## Что где лежит

| Путь | Что это |
| --- | --- |
| `/opt/nexora-panel/nexora-panel` | бинарник |
| `/opt/nexora-panel/config.json` | только подключение к базе |
| `/var/opt/nexora/nexora.db` | база SQLite |
| `/var/opt/nexora/bin/` | бинарники узлов, которые панель отдаёт установщикам |
| `/var/opt/nexora/sub-themes/` | темы страницы подписки |
| `/var/opt/nexora/presets/` | файлы каталога пресетов, накладываемые на встроенный |
| `/var/opt/nexora/backups/` | архивы копий и снимки до восстановления (права 0700) |
| `/var/opt/nexora/rulesets/` | зеркальные файлы наборов правил, которые панель отдаёт узлам |
| `/etc/systemd/system/nexora-panel.service` | unit службы |

Всё остальное — администраторы, настройки, сертификаты, узлы, пользователи —
живёт в базе данных и управляется из панели.
