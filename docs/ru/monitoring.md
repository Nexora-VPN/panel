# Мониторинг

Панель публикует свои показатели на `/metrics` в формате Prometheus, а этот
репозиторий содержит конфигурацию scrape, дашборд Grafana и оверлей
docker-compose, который поднимает обе службы рядом с вашей панелью.

## Быстрый старт с Docker

Это **оверлей**: он добавляет Prometheus и Grafana к тому compose-файлу, который
вы уже запускаете, поэтому они попадают в сеть панели и обращаются к ней по имени
службы. Панели не нужен дополнительный опубликованный порт.

```bash
# 1. Положите каталог monitoring рядом с вашим docker-compose.yml
curl -fsSL https://github.com/nexora-vpn/panel/archive/refs/heads/main.tar.gz \
  | tar -xz --strip-components=1 panel-main/monitoring

# 2. Создайте токен в панели (ниже) и положите его в файл, который читает Prometheus
printf '%s' 'ВСТАВЬТЕ-ТОКЕН' > monitoring/prometheus/token

# 3. Задайте пароль Grafana
cp monitoring/.env.example .env      # либо добавьте эти строки в имеющийся .env
${EDITOR:-nano} .env

# 4. Запустите
docker compose -f docker-compose.yml -f monitoring/docker-compose.monitoring.yml up -d
```

**Дальше всегда указывайте оба файла `-f`.** Compose считает переданные ему файлы
полным описанием проекта, поэтому обычный `docker compose up -d` потом снова
удалит эти две службы. Если это легко забыть — задайте один раз:

```bash
echo 'COMPOSE_FILE=docker-compose.yml:monitoring/docker-compose.monitoring.yml' >> .env
```

Затем откройте Grafana. Она опубликована только на loopback: это ещё один вход в
систему, и не тот, который вы продаёте.

```bash
ssh -L 3000:localhost:3000 you@your-server
# затем откройте http://localhost:3000 и войдите с GRAFANA_PASSWORD
```

Дашборд **Nexora fleet** уже там, в папке Nexora, с настроенным источником
данных. Импортировать ничего не нужно.

Prometheus намеренно **не публикуется вовсе**. У него нет собственной
аутентификации, а держит он всю вашу операционную картину; публикация свела бы на
нет причину, по которой `/metrics` требует токен. Grafana обращается к нему
внутри сети compose.

### Если панель сама терминирует TLS

Этот запрос никогда не покидает сеть Docker, но если панель сама отдаёт HTTPS
(Настройки → Веб, режим `self_signed` или `files`), Prometheus должен говорить с
ней по HTTPS. В `monitoring/prometheus/prometheus.yml`:

```yaml
    scheme: https
    tls_config:
      insecure_skip_verify: true
```

Пропуск проверки здесь **корректен**, а не срезание угла: сертификат панели
выписан на имя, которым пользуются ваши клиенты, а не на имя службы `panel`,
к которому обращается Prometheus, — строгая проверка отвергла бы совершенно
правильный сертификат.

### Если панель живёт на базовом пути

`/metrics` переехал вместе с ней. Укажите
`metrics_path: /ваш-базовый-путь/metrics`.

### Если задано имя хоста панели

`/metrics` находится внутри монтирования панели, поэтому отвечает только на
собственное имя панели. С заданным **Настройки → Веб → Домен** (`web_domain`)
scrape по IP хоста или по имени сервиса `panel` получает то же, что и любое
другое имя, — маскировку или 404 — и в логе панели об этом ничего нет. Целью
должно быть имя хоста: дайте сервису панели это имя как сетевой алиас в вашем
compose-файле (`networks: { default: { aliases: [panel.example.com] } }`) и
собирайте с `panel.example.com:2095`, а если Prometheus в другом месте —
собирайте с настоящего имени хоста. Порт в сравнении не участвует; совпасть
должно только имя.

## Токен

`/metrics` требует аутентификации, как и любой другой маршрут, и режима без неё
нет. Документ называет каждый ваш узел и его адрес — эндпоинт, который отдаёт это
всем подряд, уже нельзя «отозвать» после того, как установки начали им
пользоваться.

В панели: **Администраторы → API-токены → добавить**, область **`stats:read`** и
ничего больше. Эта область покрывает только наблюдаемость и никаких данных, о
которых вы бы беспокоились.

Положите токен в `monitoring/prometheus/token` — в отдельный файл, а не значением
внутри `prometheus.yml`, потому что конфиг вставляют в issue и в чаты, а учётные
данные не должны путешествовать вместе с ним. `.gitignore` репозитория уже его
исключает.

Отзыв токена в панели немедленно прекращает scrape; ничего не кэшируется.

## Без Docker

Собирать метрики может любой Prometheus. Минимум:

```yaml
scrape_configs:
  - job_name: nexora-panel
    scheme: https
    metrics_path: /metrics
    authorization:
      type: Bearer
      credentials_file: /etc/prometheus/nexora-token
    static_configs:
      - targets: ['panel.example.com']
```

Интервала в 60 секунд достаточно: показатели хоста за сериями диска и памяти
снимаются раз в пять минут, а счётчики трафика кумулятивны, так что между
опросами ничего не теряется.

Для Grafana импортируйте
`monitoring/grafana/dashboards/nexora-fleet.json`. Он ссылается на источник
данных Prometheus с uid `nexora-prometheus`: либо дайте своему источнику этот
uid, либо один раз замените его в JSON.

## Что экспортируется

Всё перечисленное — это либо по узлу, либо по фиксированной категории, либо по
всему флоту.

**Панель**

| Метрика | Значение |
| --- | --- |
| `nexora_panel_build_info` | 1, с версией сборки в метке |
| `nexora_panel_start_time_seconds` | когда текущий процесс панели поднял слушатель; `time() - это` — его аптайм |

**Лицензия**

| Метрика | Значение |
| --- | --- |
| `nexora_license_valid` | 1, когда лицензия в порядке; 0 на бесплатном уровне или при любом недействительном состоянии |
| `nexora_license_expires_at_seconds` | срок действия. Отсутствует, если лицензия бессрочная |
| `nexora_license_limit{resource}` | лимит на пользователей (`resource="user"`) и узлы (`"node"`) — только они ограничены; −1 означает «без ограничения» |
| `nexora_license_used{resource}` | сколько строк учтено против этого лимита |

**Аккаунты**

| Метрика | Значение |
| --- | --- |
| `nexora_users_total{status}` | аккаунты по статусу: active, disabled, expired, limited, pending |
| `nexora_users_online` | аккаунты с трафиком внутри окна «онлайн» |

**Узлы** — у всех есть метки `node` (имя) и `id`.

| Метрика | Значение |
| --- | --- |
| `nexora_nodes_total` | сколько узлов известно панели |
| `nexora_node_up` | 1, если последний heartbeat подключился |
| `nexora_node_enabled` | 1, если вы держите узел включённым |
| `nexora_node_traffic_bytes_total{direction}` | трафик, учтённый узлу с момента добавления |
| `nexora_node_online_users` | различные аккаунты с трафиком на этом узле в окне «онлайн» |
| `nexora_node_connections` | соединения, которые держит движок узла |
| `nexora_node_engine_restarts_total` | перезапуски движка с момента старта агента узла |
| `nexora_node_disk_bytes`, `nexora_node_disk_used_bytes` | корневая файловая система |
| `nexora_node_memory_bytes`, `nexora_node_memory_used_bytes` | ОЗУ хоста |
| `nexora_node_load1` | средняя загрузка за минуту |

**Шина событий** — единственный отказ панели, который иначе проходит беззвучно:
доставка, которая так и не дошла, по построению никому об этом не сообщает.

| Метрика | Значение |
| --- | --- |
| `nexora_event_deliveries{status}` | доставки по статусу: pending, delivered, dead |
| `nexora_event_subscribers` | сколько подписчиков включено |

## Два правила, которые стоит знать

**Показателя, который узел не сообщил, нет вообще — не как нуля.** Диск, память,
загрузка, соединения, перезапуски движка и число онлайн по узлу условны: узел со
старым агентом или платформа без `/proc` не сообщают их, и панель экспортирует
**ничего**, а не ноль. Ноль нарисовал бы график, на котором диск сам собой
опустел, а все ушли офлайн. Поэтому **разрыв на таком графике значит, что панель
не знает**, а не что значение упало — ровно так же это рисует и собственная
полоса аптайма узла в панели.

Единственное исключение — `nexora_event_deliveries`, который всегда сообщает
каждый статус. Алерт на «мёртвые» доставки должен уметь вычисляться на здоровой
панели, иначе на нездоровой он никогда не сработает.

**Ничего не помечено по аккаунту.** Одна метка на пользователя — это один
временной ряд на пользователя на всю глубину хранения: десять тысяч клиентов —
десять тысяч рядов, которые никогда не уходят, и это обычный способ превратить
стек мониторинга в то, что падает первым. Вопросы уровня аккаунта отвечает
страница **Отчёты** самой панели — её можно спросить о периоде, а не опрашивать
вечно.

## Полезные алерты

Четыре, которые оправдывают шум. Пороги подстройте под свой флот.

```yaml
groups:
  - name: nexora
    rules:
      # Панель перестала отвечать. Всё остальное — следствие, поэтому окно
      # должно быть короче перезапуска и длиннее, чем один перезапуск.
      - alert: NexoraPanelDown
        expr: up{job="nexora-panel"} == 0
        for: 5m

      # Узел, который по мнению панели должен работать, не отвечает. Половина с
      # `enabled` важна: выключенный вами узел — не авария.
      - alert: NexoraNodeDown
        expr: nexora_node_up == 0 and nexora_node_enabled == 1
        for: 10m

      # Заполнившийся диск останавливает узел без предупреждения. Панель и сама
      # поднимает событие node.disk_high на 90%; это копия, которая дойдёт до
      # вас даже без установленного аддона уведомлений.
      - alert: NexoraNodeDiskFilling
        expr: nexora_node_disk_used_bytes / nexora_node_disk_bytes > 0.9
        for: 30m

      # Доставки, которые сдались. Больше об этом не сообщает ничто: вебхук,
      # который не дошёл, по построению ничего не говорит своему получателю.
      - alert: NexoraEventDeliveriesDead
        expr: increase(nexora_event_deliveries{status="dead"}[1h]) > 0
```

Если вы продаёте по лицензии, стоит добавить и алерт на неё:
`nexora_license_valid == 0` либо
`nexora_license_expires_at_seconds - time() < 7 * 86400`. Отсрочки после даты
нет, поэтому уведомление — это всё смягчение, которое есть.
