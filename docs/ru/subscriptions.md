## Как собирается подписка

Подписка пользователя — это список записей, по одной на каждый способ добраться
до вашего парка. Панель обходит узлы, на которых этот пользователь заведён, и
для каждого входящего на каждом узле пишет запись. Затем то же самое для
фронтов.

Правило, которое стоит усвоить первым, потому что оно определяет размер файла:

> **Адреса и фронты складываются. Они никогда не перемножаются.**

Три узла обслуживают один входящий, у каждого узла по два адреса, и на этом
входящем включены два доменных фронта:

```
3 узла × 2 адреса = 6 прямых записей
           2 фронта = 2 записи фронтов        ← не 6 и не 12
                      ─────────────────
                      8 записей
```

Адрес для ссылок принадлежит **узлу** — это ещё один способ добраться до той же
машины, поэтому он повторяется на каждом узле. Фронт принадлежит **входящему** —
CDN сам решает, с каким из ваших серверов говорить, по полученному имени,
поэтому один фронт покрывает сколько угодно узлов, обслуживающих этот входящий,
и пишется один раз.

Ничего из этого не отправляется на узлы: адреса для ссылок, фронты и названия
записей читаются в момент, когда клиент скачивает подписку. Правка действует со
следующего скачивания — без синхронизации и без перезапуска ядра.

## Несколько адресов на узел

**Узлы → строка узла → изменить → Адреса для ссылок.** До четырёх.

Каждая строка — адрес: IP, домен или адрес IPv6, записанный без скобок, — и
необязательная метка. Каждый адрес добавляет по копии каждой записи этого узла,
поэтому узел с тремя адресами даёт по три записи на каждый свой входящий.

```
Адреса для ссылок
├─ Прямой     203.0.113.10
├─ CDN        cdn.example.com
└─             2001:db8::10
```

Для чего нужна каждая часть:

- **Первая строка — основная.** Эндпоинты (WireGuard, OpenVPN, OpenConnect),
  скачиваемые конфигурации приложений и туннели используют только её: файл
  `.conf` сохраняется один раз и не может нести альтернативы. Поэтому
  перестановка списка меняет то, что они получают.
- **Метка задаёт название записи.** Адрес с меткой добавляет её суффиксом к
  названию записи; адрес без метки — сам адрес. Первый адрес добавляет суффикс
  **только** если у него есть метка — именно это не даёт названиям, которые ваши
  клиенты уже импортировали, сдвинуться в день, когда вы добавите второй адрес.
- **`nodes.address` не затрагивается.** Там панель обращается к узлу по mTLS, а
  здесь — то, что попадает в клиентские ссылки. Они могут полностью различаться,
  и в этом смысл: панель может достигать узла по приватному адресу, пока клиенты
  ходят на публичный.

Туннель набирает **все** адреса своей цели как failover, все под одним именем
пира, поэтому заблокированный адрес стоит только тех линков, что он нёс, а не
самого туннеля. Оба остаются подключёнными — холодного резерва, который нужно
прогревать, здесь нет.

## Доменный фронтинг

Доменный фронт — это **имя хоста CDN, к которому ваши клиенты подключаются
вместо узла**. CDN сам завершает TLS, по полученному имени понимает, на какой
origin переслать, и открывает собственное соединение к вашему серверу. Для сети,
наблюдающей за клиентом, соединение идёт на Cloudflare.

**Доменный фронтинг** в боковом меню — это каталог: до восьми фронтов, каждый
включается на тех входящих, которые он фронтит. То же членство редактируется с
другой стороны, на вкладке **Доменный фронтинг** самого входящего — это один
список, видимый с той страницы, на которой вы находитесь. Один входящий несёт не
больше четырёх.

### Как настроить

| Поле | |
| --- | --- |
| **Метка** | называет фронт и добавляется суффиксом к его записям, чтобы два фронта на одном входящем различались по выбранному вами, а не по «-2» |
| **Адрес** | имя хоста, к которому подключаются клиенты, — CDN-овское. `*.cdn.example.com` даёт каждому клиенту своё (ниже) |
| **Порт** | пусто — 443. Это порт CDN, он никак не связан с портом входящего, который видит только origin |
| **SNI** | пусто — отправляется собственное имя фронта, чего CDN и ожидает. Заполняйте, только если вашему CDN нужно другое имя на origin |
| **Заголовок Host** | пусто — следует за SNI |
| **ALPN, отпечаток, allow insecure** | TLS клиента в сторону CDN |
| **Узел-источник** | необязательно; см. ниже |
| **Входящие** | какие входящие доступны через этот фронт. Предлагаются только протоколы, которые CDN способен нести |

Запись, созданная фронтом, **заменяет** адрес, порт, SNI, заголовок Host, ALPN и
отпечаток и **убирает** пин сертификата и диапазон port hopping. Пин убран не по
недосмотру: CDN предъявляет свой сертификат, поэтому пин, вычисленный по
выданному панелью, был бы отказом в рукопожатии, причину которого клиент не
объясняет.

У фронта намеренно нет пути. Путь CDN-маршрута — это путь самого фронтируемого
входящего, и панель его уже знает.

Со стороны CDN нужно то же, что и любому CDN: имя хоста проксируется (в терминах
Cloudflare — оранжевое облако) и указывает на адрес узла как на origin, а если
входящий за CDN говорит открытым HTTP — настройка origin, которая это разрешает.
Открытый HTTP до origin — нормальный и частый случай: TLS-сессия клиента идёт с
CDN, а не с вашим узлом.

### Отдельное имя хоста каждому клиенту

Запишите адрес как `*.cdn.example.com`, и каждый подписчик получит собственное
имя под ним — `k7m2rq9xdp.cdn.example.com` одному, `bt4njs6wzv.cdn.example.com`
следующему.

Это стоит делать: самый частый способ, которым эта возможность умирает, — имя
хоста CDN попадает в список блокировок. С wildcard одно заблокированное имя
стоит одного клиента, а не всех сразу.

**Нужна wildcard-запись DNS** — `*.cdn.example.com`, указывающая на CDN и
проксируемая как любая другая. Без неё имя не разрешается ни у кого, и выглядит
это ровно так же, как отказ CDN.

Метка выводится из собственного токена подписки клиента, а не случайна: она та же
самая при каждом обновлении у клиента — конфигурация, меняющаяся на каждом
опросе, была бы хуже отсутствия wildcard — и разная у каждого клиента. Это
односторонняя функция от токена: имя хоста в списке блокировок ничего не говорит
о токене за ним.

### Узел-источник

**Узел-источник** ничего не умножает — фронт по-прежнему даёт одну запись на
входящий. Он говорит, на какой из ваших серверов пересылает CDN, и панель
использует его ровно для двух вещей: не класть фронт в файл пользователю, который
на этом узле не заведён (там ссылка всё равно не смогла бы авторизоваться), и
предупредить, когда названный узел не обслуживает входящий, на котором фронт
включён.

Оставьте поле пустым, если решает ваш CDN, — тогда ни одна из проверок не
выполняется.

### Только через фронт

Переключатель **Только через фронт** у входящего убирает его прямые записи из
подписки — адрес узла тогда не появляется в файле этого клиента нигде, ради чего
фронтинг и затевался.

Он действует **на каждого пользователя отдельно и только там, где фронт для него
действительно отрисовался**. Иначе фронт, привязанный к узлу-источнику, до
которого конкретный клиент не достаёт, опустошил бы его файл, ничего не объяснив.
Если фронтов не включено вовсе, переключатель ничего не делает и прямые записи
продолжают отрисовываться.

### Что нельзя фронтить и что делать вместо этого

Панель отклоняет такие пары **при сохранении**, с любой стороны, а не молча
выбрасывает запись при сборке подписки. Причина всегда одна и та же фраза:
**CDN завершает TLS и пересылает HTTP.**

| Отклоняется | Почему |
| --- | --- |
| **REALITY** | привязывает рукопожатие к собственному ключу входящего, а CDN предъявляет свой сертификат. Конфигурации, в которой это работает, не существует |
| **Hysteria, Hysteria2, TUIC** | работают поверх QUIC, то есть UDP. Граница HTTP/3 сама завершает QUIC-сессию и говорит с origin своим протоколом — от прокси ничего не доезжает |
| **Port hopping** | набор портов принадлежит собственному слушателю узла. Фронт — это одно имя хоста на одном порту |
| **Чистый TCP, AnyTLS, ShadowTLS, SOCKS, SSH, mieru…** | CDN, завершающий TLS, никак не может нести поток, который не является HTTP-запросом |

Пригодные транспорты: **WebSocket, HTTPUpgrade, gRPC, XHTTP и HTTP/2**.

Для всего из этого списка ответ — **второй адрес на узле**, а не фронт. Релей,
пересылающий чистый TCP и ничего не завершающий, несёт их все прекрасно — и для
этой панели такой релей является ещё одним адресом в списке адресов узла, а не
CDN-маршрутом.

Входящий, сохранение которого было бы отклонено, вообще не предлагается в
выборе входящих у фронта, и выбор объясняет почему.

### Если входящий стоит за ingress

Ingress маршрутизирует по имени из TLS-рукопожатия. CDN открывает **собственное**
соединение к origin и несёт в нём имя хоста **фронта**, а не `server_name` самого
входящего, — поэтому маршрут ingress, в котором имени фронта нет, отправит этот
трафик в fallback, а в рекомендуемой схеме это имитация веб-страницы. Ошибки не
происходит. Клиент просто никуда не приходит.

Панель предупреждает, а не отказывает, потому что маршрут и фронт пишут в любом
порядке. Добавьте имя хоста фронта в маршрут (или суффиксный шаблон
`.cdn.example.com`, который покрывает и wildcard-фронт) — и предупреждение уйдёт.

## Названия записей

**Настройки → Подписки → Имена ссылок.** По умолчанию пусто, и пусто означает,
что каждая запись сохраняет название, которое эта панель выдавала всегда.
Умолчание намеренное: клиенты привязывают сохранённый выбор пользователя к
названию записи, поэтому шаблон — то, что выбирают, а не то, что обязательно
заполняют.

Шаблон — свободный текст с `{ПЕРЕМЕННЫМИ}`:

```
{USER} · {ROUTE} · {REMAINING}        →   ali · CDN · 42.1 GB
{INBOUND}-{NODE}                      →   vless-ws-de-1
{USER_REMARK} {PROTOCOL} {DAYS_LEFT}d →   Ali VIP vless 17d
```

| Переменная | |
| --- | --- |
| `{USER}` `{USER_REMARK}` | имя учётной записи и её примечание |
| `{INBOUND}` `{PROTOCOL}` `{NETWORK}` | тег входящего, его протокол, его транспорт |
| `{NODE}` `{NODE_REMARK}` | узел, для прямой записи. У записи фронта пусто — фронт не находится на одном узле |
| `{ROUTE}` | каким путём запись достаёт до парка: метка адреса узла или метка фронта |
| `{SERVER}` `{PORT}` | то, к чему запись реально подключается |
| `{USED}` `{REMAINING}` `{TOTAL}` | трафик в удобном виде; `∞` там, где лимита нет |
| `{DAYS_LEFT}` `{EXPIRE}` | сколько дней осталось и дата; `∞` там, где срока нет |
| `{EXPIRE_JALALI}` | та же дата по солнечной хиджре |

Четыре правила, и **предпросмотр** под полем показывает все четыре на образцовой
учётной записи — его строит собственный рендерер панели, а не догадка, поэтому вы
видите ровно то, что получат клиенты:

- **Всё, чего нет в списке, остаётся ровно как написано.** `{SEVER}`
  отрисуется как `{SEVER}`, чтобы опечатка была видна, а не тихо удаляла часть
  каждого названия. Шаблон, в котором вообще нет известной переменной,
  отклоняется при сохранении: все записи получили бы одно имя.
- **Пустая переменная забирает свой разделитель.** `{USER}-{NODE}-{INBOUND}` на
  записи фронта, у которой узла нет, даёт `ali-vless-ws`, а не `ali--vless-ws`.
  Разделитель, написанный вами между двумя заполненными переменными, не трогают
  никогда.
- **Даты и величины — те же, что показывает страница подписки**, во временной
  зоне панели, чтобы название и страница не могли разойтись.
- Названия обрезаются на 128 символах, а запись, шаблон которой дал для неё
  пустоту, возвращается к фиксированному названию, а не приходит безымянной.

Скачиваемые конфигурации приложений (`.ovpn`, `.conf`) сохраняют собственные
названия. Это имена файлов, а `∞` или `/` в имени файла — проблема другого рода.

## Что сообщается клиенту

Ответ подписки несёт не только конфигурации. Клиенты, знающие эти заголовки,
показывают заголовок профиля, полосу квоты, объявление и кнопку поддержки, ничего
для этого не открывая.

| Заголовок | Откуда | Кто читает |
| --- | --- | --- |
| `Profile-Title` | **Настройки → Подписки → Заголовок профиля** или примечание пользователя | Happ, v2RayTun (в Happ ~25 символов) |
| `Subscription-Userinfo` | квота, расход и срок учётной записи | Happ, v2RayTun, Clash Meta |
| `Profile-Update-Interval` | **Интервал обновления у клиента** | Happ, v2RayTun. Clash Meta для Android игнорирует |
| `Announce` | **Объявление** | Happ (~200 символов), v2RayTun |
| `Support-Url` | **Ссылка на поддержку** | Happ |
| `Profile-Web-Page-Url` | **Предлагать ссылку на страницу подписки** | Happ |

Все шесть есть в стандарте подписок XTLS, откуда и взято их написание.
Отправляются только имена, чтение которых документирует хоть один клиент.
Заголовок, который никто не читает, — лишний вес, а написанный не так, как во
всей остальной экосистеме, — хуже: он выглядит реализованным.

Две настройки на той же странице определяют форму ответа, а не его содержимое:

- **Интервал обновления у клиента** — в часах; пусто означает 12. Поставьте `0`,
  и заголовок не отправляется вовсе, оставляя каждый клиент на его собственном
  умолчании.
- **Предлагать ссылку на страницу подписки** — выключено **убирает** заголовок, а
  не отправляет пустой, потому что пустое значение — это кнопка, которая ничего
  не открывает.

Текст не из ASCII — персидский заголовок, русское объявление — уходит в base64 за
префиксом `base64:`, именно это реализуют клиенты этой экосистемы. Переводы строк
в объявлении становятся пробелами: HTTP-заголовок — это одна строка.

## Скажите пользователям выключить Mux

У клиентов на Xray — **v2rayNG, v2rayN, Streisand** — есть переключатель **Mux**.
Включённый, он заставляет клиента говорить на `mux.cool` — протоколе
мультиплексирования, которого эти серверы не реализуют и не будут: узлы Nexora
работают на sing-box, чьё мультиплексирование является совсем другим протоколом.

С включённым Mux соединение не устанавливается. Не с ошибкой, по которой
пользователь мог бы что-то сделать, — оно просто не работает, и в ваш чат
поддержки это приходит как «конфиги сломаны».

Со стороны панели сделать нечего: помешать клиенту упаковывать собственный трафик
она не может. Поэтому предупреждение несёт сама страница подписки, на языке
клиента, на вкладке **Дополнительно**, — и его стоит повторить везде, где вы
пишете собственную инструкцию по настройке.

Настройка мультиплексирования в приложениях на sing-box и Clash — совсем другая
функция, её трогать не нужно: предупреждение про ту, что в Xray.
