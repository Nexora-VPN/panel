# 选择数据库

Nexora 可以跑在 SQLite 或 PostgreSQL 上。安装脚本两者都不会问你——不加
`--postgres` 就用 SQLite——因为对多数面板来说这个选择无关紧要，而对少数确实有影响
的面板来说，起决定作用的那个数字你本来就知道：**同时有多少用户在跑流量**。

本页是我们的建议、建议的依据，以及超出这个范围之后该怎么办。

## 简要结论

| 情况 | 数据库 |
| --- | --- |
| 同时活跃用户不超过约 10,000 | **SQLite** |
| 同时活跃用户超过约 25,000，或在慢盘上超过约 10,000 | **PostgreSQL** |
| 数据库文件会放在 NFS、网络卷或任何共享存储上 | **PostgreSQL**，无论规模 |
| 多个面板进程共用一个数据库 | **PostgreSQL**，无论规模 |
| 你已经在运行 PostgreSQL 服务器 | **PostgreSQL**——额外成本为零 |

“同时活跃”指的是节点在同一个 30 秒采集周期内上报了流量的用户，而不是数据库里的
用户数。一个有 50,000 个账号、峰值在线 3,000 人的面板，在这里算 3,000 用户的面板。

**节点数量几乎没有影响。** 一个用户同一时刻只经由一个节点，所以十个节点合计服务
10,000 名用户的开销，和一个节点服务 10,000 名用户差不多；每多一个节点，只多出它自己
那几个 inbound 计数器。

两个阈值之间，两者都可以。如果你看重“只有一个文件可以复制”，选 SQLite；如果你不
想再回头重新决定，选 PostgreSQL。

## 这些数字从何而来

面板对数据库做的事都很小、很平稳——操作员打开一个页面，客户端拉取一次订阅——只有
一件事例外。每 30 秒，面板会把每个节点的流量计数器取空并写入：每个用户的累计量、
每个节点的汇总，以及用量图表所依据的采样。这一次写入洪峰的大小正比于活跃用户数，
而且是一个事务。

它的实测代价如下——一次取空写入到一个按面板方式调优过的、基于文件的 SQLite 数据库，
盘是 NVMe：

| 同时活跃用户 | 写入一次取空的耗时 |
| --- | --- |
| 100 | 3 毫秒 |
| 1,000 | 39 毫秒 |
| 5,000 | 153 毫秒 |
| 10,000 | 319 毫秒 |

相对于 30 秒的周期，即使是最后一行也只占用写入路径约 1% 的时间。这就是上面的阈值定
在那里而不是更低的原因——也是为什么第二列这个数字值得在**你自己的**硬件上实测，而不
是照搬本表：廉价 VPS 的磁盘可能比测这组数字的盘慢上数倍。在源码目录里：

```sh
go test ./internal/service/ -run '^$' -bench BenchmarkAccount -benchtime 10x
```

SQLite 同一时刻只允许一个写入者，作用范围是整个文件。洪峰写入期间，其他任何写入都
要等待。Nexora 对 SQLite 做了配置，让它们**等待**而不是报错（见下文）——这是“慢一
分钟”和“出错”的区别——但等待终究是等待，超过某个规模，下一次洪峰会在上一次还没写完
时就到来。

PostgreSQL 写的是行而不是文件：记账洪峰和其他工作同时进行，而且读取者根本不会被写
入者阻塞。差别就在这里。并不是 PostgreSQL 更快——对小面板来说它明显更慢，因为每条
语句都是一次经过套接字的往返，而不是面板进程内部的一次函数调用。

所以：没有写入争用时 SQLite 更快，而 PostgreSQL 根本不在乎有没有争用。按争用来选，
不要按规模来选。

## 哪些不构成迁移的理由

- **账号数量。** 十万行对 SQLite 不算什么。有代价的是为它们写入流量，而休眠账号什
  么也不写。
- **提供订阅的次数。** 那些是读取，而在 WAL 模式下（面板会启用它）读取者永远不会被
  阻塞。
- **对可靠性的笼统担忧。** SQLite 不会因为崩溃或断电而丢掉数据库，它是世界上受测试
  最充分的软件之一。它输在**共享存储**和**两个进程**上——这正是上表那两行无论规模
  都写 PostgreSQL 的原因。

## 面板已经替你做的调优

两种数据库都不会停留在默认值上，你也不需要自己配置。无论安装脚本在 `config.json`
里写的是哪一种，面板每次启动都会应用：

**SQLite**

| 设置 | 取值 | 原因 |
| --- | --- | --- |
| `journal_mode` | WAL | 默认模式会在每次写入的全过程阻塞所有读取者。WAL 让读取者在写入进行时从最后一次提交的快照读取。 |
| `synchronous` | NORMAL | 这是 WAL 有文档背书的安全搭配：崩溃不会损坏数据库，只会丢失最后若干事务。FULL 意味着每次提交一次 fsync，而这正是廉价磁盘显得“坏掉了”的原因。 |
| `busy_timeout` | 10 秒 | 遇到争用的写入者会等待，而不是返回 “database is locked”。 |
| `cache_size` | 每连接 8 MiB | 足以容纳每分钟检查所需的用户表。 |
| `_txlock` | immediate | 微妙的一条。先读后写的事务无法等待锁——在别的写入者持锁时提升读锁是死锁而不是等待，无论超时设多长都会立刻失败。一开始就取写锁，就把它变成了普通的等待。 |
| 连接池 | 8 个连接 | 读取者受益于多于一个；写入者无论如何都要排队。 |

**PostgreSQL**

| 设置 | 取值 | 原因 |
| --- | --- | --- |
| 连接池 | 20 个连接，5 个空闲 | 给该服务器的其他使用者留出余地：`max_connections` 默认是 100，并且与主机上其他一切共享。 |
| 连接存活时间 | 30 分钟 | 长期运行的面板不会在整个运行期间占住服务端内存，或占住一个此后可能已经故障切换的实例的连接。 |

唯一值得覆盖的数字是连接池大小，而且只在与其他应用共用的 PostgreSQL 服务器上。写在
`config.json` 里：

```json
{ "db": { "driver": "postgres", "dsn": "…", "max_open_conns": 10 } }
```

或者在环境变量里 `NEXORA_DB_MAX_OPEN_CONNS=10`。其他情况请不要动它。

你自己在 SQLite DSN 里写明的任何 pragma 都会被保留——面板是往你的 DSN 上追加，而不
是跟它对着来。

## 以后再迁移

你并没有被锁死。Nexora 的备份是逻辑导出，每张表一个文件，而不是数据库文件的副本
——所以在一种数据库上做的归档可以恢复到另一种上，这也正是双向迁移受支持的方式：

1. 在旧面板上：**备份 → 创建**，下载归档。
2. 把面板安装或改配到新数据库上（`config.json` 里的 `driver` 和 `dsn`，或者用
   `--postgres` 全新安装）。
3. 在新的空面板上恢复该归档——若尚未配置就在初始设置向导里恢复，已配置则用
   **备份 → 恢复**。

恢复会重写所有管理员账号，因此之后请用旧面板的凭据登录。许可证和本机自身的地址设置
会被保留而不是取自归档，因为两者都与这台机器绑定。

有两样东西在数据库之外、也在归档之外，如果你同时更换主机就需要手动搬运：主题目录里
的订阅页面主题，以及暂存的节点二进制文件。节点本身什么都不需要——它们不保存状态。

## 数据库在哪里

用 SQLite 时它是单个文件，默认为 `/var/opt/nexora/nexora.db`，面板运行期间旁边还有
`-wal` 和 `-shm`。**在面板运行时复制这三个文件不算备份**——请使用面板自带的备份，它
无需停止任何东西就能取得一致的快照。

用 PostgreSQL 时，面板只保存一个连接串；按你惯用的方式备份那台服务器，或者使用面板
自带的备份——它在两种数据库上是一样的。
