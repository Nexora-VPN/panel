## 一份订阅是怎么组成的

用户的订阅是一串记录，每一条对应一条能连到你机群的路径。面板遍历该用户被开通
的节点，为每个节点上的每个入站写一条记录；然后对前置做同样的事。

最先该记住的规则，因为它决定文件有多大：

> **地址和前置是相加，永远不是相乘。**

三个节点服务同一个入站，每个节点列两个地址，该入站上启用了两个域名前置：

```
3 节点 × 2 地址 = 6 条直连记录
          2 前置 = 2 条前置记录        ← 不是 6 条，也不是 12 条
                   ──────────────
                   8 条记录
```

链接地址属于**节点**——它是抵达同一台机器的另一条路，所以每个节点各算一遍。前置
属于**入站**——CDN 是根据收到的名字自行决定与你哪台服务器通信的，所以一个前置覆盖
服务该入站的所有节点，只写一次。

链接地址、前置和记录名称都是在客户端拉取订阅时才读取的，因此修改在下一次拉取时
即刻生效，无需同步。唯一的例外是前置的*客户端地址头*：改变 XHTTP 入站所信任的头
的保存或删除，会下发到服务该入站的每个节点，在那里重启该入站并断开其现有连接。
其他任何修改都不会到达节点。

## 链接发布在哪里

在这一切之前：文件是*从哪个*地址取回的。它和面板自己的地址不是一回事，面板也
刻意把两者分开——面板的路径本该保持私密，而订阅地址要交给你的每一个客户。

**设置 → 订阅 → 订阅域名。**

列在那里的每一个域名都提供 `/sub`，而在这些名字上，面板只能通过它的**基础路径**
访问——在根路径请求 API 或登录页只会得到 404，所以客户手里的地址不会透露面板在哪
里管理。（没有设置基础路径时就没有什么可躲的，那些名字就只提供订阅、别的什么都不
提供。这也是这项设置唯一一种会把你自己挡在面板之外的方式，见安装指南的“被挡在门
外？”。）

### 为什么是一个列表

因为域名被封是会发生的事，而到那时链接早已在客户的客户端里了。

- **新链接在第一个域名上生成。**
- **列表里的每个域名都继续提供服务**——为它在第一位时发出的那些链接。

所以替换一个被封的域名就是：加上新的，把它移到最上面，并把旧的留在列表里，让客
户按自己的更新节奏切换过去。把它从列表里删掉，才是最终切断那些链接的动作，而这
是你来决定的，不是添加替代域名的副作用。

### 每一个需要什么

一条指向面板的 DNS 记录，以及面板证书上的一个位置。保存这项设置会重新签发面板
自己的证书，让它涵盖列表里的每一个域名。如果证书由你自己管理——`web_cert_file` /
`web_key_file`，或证书库里的一张——那每个名字都要你自己放上去：证书没有覆盖的域
名，在客户端是一个 TLS 错误，而不是一条只不过渲染到了别处的链接。

最多八个。列表留空，链接就用打开面板时所用的地址构建——单服务器、没有域名的安装
正需要这样。

### 每位客户一个主机名

列表里的域名可以写成带 `*` 的形式：

```
*.sub.example.com
```

这样每位订阅者都会拿到它下面**各自的主机名**——一个是
`k4m2xr8qvp.sub.example.com`，下一个是 `bt7wz3ncdh.sub.example.com`——而面板对它
们全都应答。一个被封的主机名只损失**一位客户**，而不是你的整本客户名册；这是一
张工单和糟糕一周之间的差别。

让它真正管用、而不只是听着不错的，是这三点：

- **它是推导出来的，不是随机的。** 标签是账号的哈希，所以重新拉取订阅的客户拿到
  的还是同一个主机名。每次轮询都在变的名字，会把所有已经保存过它的客户端弄坏。
- **它是单向的。** 哈希只进不出：出现在封锁名单上的主机名，说明不了它背后的订阅
  令牌。
- **它按域名各不相同。** 同一位客户在你配置的每个域名下都会得到互不相关的标签，
  所以封掉一个名字不会泄露替代域名上的任何线索。

**你需要一条通配符 DNS 记录**，即指向本面板的 `*.sub.example.com`。这一步绕不
过，也没有任何东西能提醒你漏了它：没有这条记录，这些主机名谁都解析不到，而这看
起来和域名被封一模一样。面板自己的证书会自动覆盖通配符；如果证书由你自己管理，
上面就必须有 `*.sub.example.com` 这个名字。

只服务恰好一层标签。`abc.sub.example.com` 可以，`a.b.sub.example.com` 不行——通
配符 DNS 记录解析的、通配符证书覆盖的都只有一层，所以再深一层本来也够不着。

普通条目完全不受这些影响。想让所有人共用一个主机名的安装不需要做任何 DNS 工作，
渲染结果和以前一模一样。

### 每个分销商一个域名

**管理员 → 该分销商 → 编辑 → 订阅域名**，只有主管理员能设置。

它决定这个分销商的客户发布在你配置的哪个域名下。不动它，他们就用第一个。分销商
不能改自己的：域名正是被整体封禁的单位，所以选域名就是在选谁的客户会一起失联，
而这不是一个分销商该替别人的客户名册做的决定。

两种机制是叠加而不是互斥的：给每个分销商一个通配符域名，一个被封的主机名损失一
位客户，一个被封的*域名*损失一个分销商。

如果你删掉了某个分销商被指派的域名，该分销商会回退到第一个已配置的域名，而不是
无处可去。把域名移出列表本来就是让它退役的方式，它不该顺带让一个分销商的整本名
册下线。

### 关于规则集的一点说明

节点从这同一个发布地址下载镜像的规则集，而节点拨的是一个*名字*——
`*.sub.example.com` 不是名字。所以镜像会用列表里第一个**普通**域名；如果所有条
目都是通配符，就用 `rulesets.sub.example.com`，它已经被你的通配符 DNS 记录和证
书覆盖。规则集页面会显示最终选定的地址。

## 一个节点配多个地址

**节点 → 该节点所在行 → 编辑 → 链接地址。**最多四个。

每一行是一个地址——IP、域名，或直接写出的 IPv6 地址——外加一个可选的标签。每个
地址都会为该节点贡献的每条记录再加一份副本，所以配了三个地址的节点，它的每个入站
都有三条记录。

```
链接地址
├─ 直连      203.0.113.10
├─ CDN       cdn.example.com
└─            2001:db8::10
```

各部分的用处：

- **第一行是主地址。**端点（WireGuard、OpenVPN、OpenConnect）、可下载的应用配置
  和隧道都只用它：`.conf` 文件保存一次，无法携带备选项。因此调整列表顺序会改变它们
  拿到的地址。
- **标签决定记录名称。**带标签的地址会把标签作为后缀加到记录名上；不带标签的则回退
  为地址本身。第一个地址**只有**带标签时才加后缀——正是这一点，保证你加上第二个地址
  的那天，客户已经导入的名称不会发生变化。
- **`nodes.address` 不受影响。**那是面板通过 mTLS 连接节点的地方，而这里是写进客户端
  链接的内容。两者完全可以不同，这正是要点：面板可以走私网地址连节点，而客户走公网
  地址。

隧道会把目标的**所有**地址都作为故障转移拨号，且全部挂在同一个 peer 名下，因此某个
地址被封只损失它承载的链路，而不是整条隧道。两边都保持连接——这里没有需要预热的
冷备。

## 域名前置

域名前置就是**让客户连 CDN 的主机名，而不是连节点**。CDN 自己终结 TLS，根据收到的
名字判断该转发到哪个源站，再向你的服务器发起它自己的连接。在监视客户的网络看来，
这条连接是去 Cloudflare 的。

侧边栏的**域名前置**是目录：最多八个前置，每个在它所前置的入站上启用。同一份归属
关系也可以从另一端编辑，即入站自己的**域名前置**标签页——这是同一份列表，取决于你
在哪个页面看它。单个入站最多带四个。

### 如何配置

| 字段 | |
| --- | --- |
| **标签** | 给前置命名，并作为它生成记录的后缀，这样一个入站上的两个前置靠你选定的名字区分 |
| **地址** | 客户端连接的主机名——CDN 的那个。写成 `*.cdn.example.com` 可让每个客户各有一个（见下） |
| **端口** | 留空即 443。这是 CDN 的端口，与入站的监听端口无关，后者只有源站看得到 |
| **SNI** | 留空即发送前置自己的主机名，这也是 CDN 所期待的。只有当你的 CDN 在源站需要另一个名字时才填 |
| **Host 头** | 留空即跟随 SNI |
| **ALPN、指纹、allow insecure** | 客户端朝 CDN 方向的 TLS |
| **源节点** | 可选；见下 |
| **入站** | 经由此前置可达的入站。只会列出 CDN 确实能承载的协议 |

前置生成的记录会**替换**地址、端口、SNI、Host 头、ALPN 和指纹，并**去掉**证书 pin
以及端口跳跃范围。去掉 pin 不是疏忽：CDN 出示的是它自己的证书，按面板签发的证书算
出来的 pin 会导致握手失败，而客户端不会说明原因。

前置刻意没有 path。CDN 路由的 path 就是被前置入站自己的 path，面板已经知道。

CDN 那一侧需要的和任何 CDN 一样：主机名开启代理（Cloudflare 的说法是橙色云朵），
源站指向节点地址；如果入站在 CDN 后面走的是明文 HTTP，还要打开允许这样做的源站
设置。到源站走明文很常见也没问题：客户的 TLS 会话是和 CDN 建立的，不是和你的节点。

### 每个客户一个主机名

把地址写成 `*.cdn.example.com`，每位订阅者都会在它下面得到自己的主机名——一位是
`k7m2rq9xdp.cdn.example.com`，下一位是 `bt4njs6wzv.cdn.example.com`。

这么做很值得，因为这项能力最常见的死法就是某个 CDN 主机名进了封锁名单。有了泛
域名，一个被封的名字只损失一位客户，而不是全部。

**它需要一条泛域名 DNS 记录**——`*.cdn.example.com` 指向 CDN，和其他记录一样开启
代理。没有它，这个名字对谁都解析不了，而那看起来和 CDN 拒绝连接一模一样。

**在 Cloudflare 上要留意名字有多深。** 区域免费拿到的 Universal SSL 证书覆盖
`example.com` 和它下面的**一**级标签，也就是 `*.example.com`；它不覆盖
`*.cdn.example.com`——那要再深一级。其他一切看起来都没问题：记录能解析，橙色云
是开的，CDN 明明就在路径上。实际发生的是：边缘没有可以为该名字出示的证书，TLS
握手就死在那里，任何东西都到不了你的节点。要么把泛域名直接放在区域之下——
`*.example.com`，订阅域名另外安排——要么加购 Advanced Certificate Manager 或
Cloudflare for SaaS，它们会为更深的名字签发证书。其他 CDN 有各自的规则；在怀疑
源站之前，先确认你的证书到底覆盖了什么。

标签是从客户自己的订阅令牌推导出来的，不是随机数：因此该客户端每次刷新拿到的都
一样——每次轮询都变的配置比没有泛域名更糟——而每位客户又各不相同。它是令牌的单向
函数：一个进了封锁名单的主机名，说明不了背后的令牌。

### 源节点

**源节点**不会让任何东西翻倍——前置仍然是每个入站一条记录。它说明 CDN 转发到你的
哪台服务器，面板只把它用于两件事：把前置从未在该节点开通的用户文件里拿掉（在那里
链接本来也无法通过认证），以及在你指定的节点并不服务某个已启用该前置的入站时发出
警告。

如果由你的 CDN 自行决定，就留空，这两项检查都不会执行。

### 仅经由前置

入站上的**仅经由前置**开关会把它的直连记录从订阅里去掉——节点地址便不会出现在那位
客户文件的任何位置，而这正是前置它的目的。

它是**按用户生效的，而且只在前置确实为该用户渲染出记录时才生效**。否则，一个绑定到
某位客户够不着的源节点上的前置，会把他的文件清空却什么都不说明。如果根本没有启用
任何前置，这个开关不起作用，直连记录照常渲染。

### 哪些不能前置，以及改用什么

面板在**保存时**就拒绝这些组合，且从两端都拒绝，而不是在构建订阅时默默丢弃记录。
理由永远是同一句话：**CDN 终结 TLS 并转发 HTTP。**

| 被拒绝 | 原因 |
| --- | --- |
| **REALITY** | 它把握手绑定在入站自己的密钥上，而 CDN 出示的是自己的证书。不存在让两者共存的配置 |
| **Hysteria、Hysteria2、TUIC** | 它们跑在 QUIC 上，也就是 UDP。HTTP/3 边缘节点会自行终结 QUIC 会话，再用自己的协议与源站通信，代理的内容一点都到不了 |
| **端口跳跃** | 这组端口属于节点自己的监听器。而前置是一个主机名加一个端口 |
| **裸 TCP、AnyTLS、ShadowTLS、SOCKS、SSH、mieru…** | 终结 TLS 的 CDN 无从承载一条并非 HTTP 请求的数据流 |

可以承载的传输方式是 **WebSocket、HTTPUpgrade、gRPC、XHTTP 和 HTTP/2**。

对于上表中的一切，答案是**给节点加第二个地址**，而不是前置。一个不终结任何东西、
直接转发裸 TCP 的中转，能很好地承载它们——对这个面板来说，那样的中转是节点链接
地址列表里的又一个地址，而不是一条 CDN 路由。

保存会被拒绝的入站，根本不会出现在前置的入站选择器里，选择器还会说明原因。

### 如果入站在 ingress 后面

ingress 按 TLS 握手中的名字做路由。CDN 会开启**它自己**到源站的连接，并在其中携带
**前置的**主机名，而不是入站自己的 `server_name`——因此没有列出前置主机名的 ingress
路由，会把这些流量送到它的 fallback，在推荐的部署里那是一个仿真网页。不会有任何
报错。客户只是永远到不了。

面板给出警告而不是拒绝，因为路由和前置的书写顺序本来就不固定。把前置的主机名加进
路由（或者加一条 `.cdn.example.com` 后缀规则，它同时覆盖泛域名前置），警告就会消失。

## 记录的命名

**设置 → 订阅 → 链接名称。**默认为空，而空表示每条记录都保留这个面板一直以来生成
的名称。这个默认值是有意的：客户端把用户保存的选择关联在记录名称上，所以模板是用来
选择的，不是非填不可的。

模板是带 `{变量}` 的自由文本：

```
{USER} · {ROUTE} · {REMAINING}        →   ali · CDN · 42.1 GB
{INBOUND}-{NODE}                      →   vless-ws-de-1
{USER_REMARK} {PROTOCOL} {DAYS_LEFT}d →   Ali VIP vless 17d
```

| 变量 | |
| --- | --- |
| `{USER}` `{USER_REMARK}` | 账号名称及其备注 |
| `{INBOUND}` `{PROTOCOL}` `{NETWORK}` | 入站的 tag、协议、传输方式 |
| `{NODE}` `{NODE_REMARK}` | 节点，用于直连记录。前置记录上为空——前置并不在某一个节点上 |
| `{ROUTE}` | 这条记录经由哪条路抵达机群：节点地址的标签，或前置的标签 |
| `{SERVER}` `{PORT}` | 这条记录实际连接的目标 |
| `{USED}` `{REMAINING}` `{TOTAL}` | 格式化后的流量；没有限额的地方是 `∞` |
| `{DAYS_LEFT}` `{EXPIRE}` | 剩余天数和日期；没有到期时间的地方是 `∞` |
| `{EXPIRE_JALALI}` | 同一个日期的伊朗历写法 |

共四条规则，字段下方的**预览**会在一个样例账号上把四条都演示出来——预览由面板自己的
渲染器生成，不是猜测，所以你看到的就是客户会拿到的：

- **不在上表中的内容，原样保留。**`{SEVER}` 就渲染成 `{SEVER}`，好让拼写错误看得见，
  而不是悄悄删掉每个名称的一部分。完全不含已知变量的模板在保存时会被拒绝，因为那样
  每条记录都会得到同一个名字。
- **空变量会带走它的分隔符。**前置记录没有节点，`{USER}-{NODE}-{INBOUND}` 渲染成
  `ali-vless-ws`，而不是 `ali--vless-ws`。你写在两个都有值的变量之间的分隔符，从不
  改动。
- **日期和数量与订阅页面显示的一致**，使用面板的时区，这样名称和页面不会互相矛盾。
- 名称在 128 个字符处截断；如果模板对某条记录渲染出空串，该记录会回退到固定名称，
  而不是无名抵达。

可下载的应用配置（`.ovpn`、`.conf`）保留各自的命名方式。那些字符串是文件名，而文件名
里出现 `∞` 或 `/` 是另一类问题。

## 告诉客户端的内容

订阅响应携带的不只是配置。认得这些响应头的客户端，不用用户打开任何东西就能显示
标题、流量条、公告和客服按钮。

| 响应头 | 来自 | 谁会读 |
| --- | --- | --- |
| `Profile-Title` | **设置 → 订阅 → 配置文件标题**，或用户的备注 | Happ、v2RayTun（Happ 约 25 个字符） |
| `Subscription-Userinfo` | 账号的限额、用量和到期时间 | Happ、v2RayTun、Clash Meta |
| `Profile-Update-Interval` | **客户端刷新间隔** | Happ、v2RayTun。Clash Meta for Android 会忽略 |
| `Announce` | **公告** | Happ（约 200 个字符）、v2RayTun |
| `Support-Url` | **客服链接** | Happ |
| `Profile-Web-Page-Url` | **提供返回订阅页面的链接** | Happ |

这六个都在 XTLS 的订阅规范里，写法也出自那里。只发送有客户端明确写明会读取的名字。
没人读的响应头是无用负担，而写法与整个生态不一致的更糟，因为它看起来像是实现了。

同一页面上有两个设置决定的是响应的形式而非内容：

- **客户端刷新间隔**——以小时计；留空表示 12。设为 `0` 则完全不发送该响应头，让每个
  客户端各自沿用默认值。
- **提供返回订阅页面的链接**——关闭是**移除**该响应头，而不是发一个空值，因为空值等于
  一个什么都打不开的按钮。

非 ASCII 文本——波斯语标题、俄语公告——会以 `base64:` 前缀加 base64 编码发送，这正是
这个生态里的客户端所实现的。公告中的换行会变成空格：HTTP 响应头只有一行。

## 请用户关掉 Mux

基于 Xray 的客户端——**v2rayNG、v2rayN、Streisand**——有一个 **Mux** 开关。打开它，
客户端就会讲 `mux.cool`，而这些服务器不实现该多路复用协议，将来也不会：Nexora 的
节点跑的是 sing-box，它的多路复用完全是另一个协议。

开着 Mux，连接就会失败。而且不是给出一个用户能据此处理的错误——它就是不工作，到你
客服那里就变成了「配置坏了」。

面板这一侧无能为力：它无法阻止客户端给自己的流量加帧。所以订阅页面会用客户自己的
语言，在**高级**标签页里给出这条提醒——而且值得在你自己写的使用说明里也重复一遍。

sing-box 和 Clash 应用里的多路复用设置是另一回事，保持默认即可——这条提醒说的是
Xray 的那个。

## 客户端导入了链接却什么都不显示

v2rayNG 把每条订阅放在各自的分组里，而**「Update subscription」只刷新当前选中的
那个分组**，不是应用里的全部分组。客户导入你的链接后，若在屏幕上停留在另一个分组
时点了更新，拿到的是一个空列表，而且**没有任何报错**：订阅已经存好，地址没错，
开关是开的，却没有任何东西说明里面为什么是空的。

要先选中新分组的标签页，再点更新。把这一条写进你自己给 Xray 系客户端的使用说明
里：它的症状和「订阅链接不能用」无法区分，所以到你客服那里时就是这么说的。
